# Вариант 18: граф зависимостей Cargo

Практическая работа № 2 по конфигурационному управлению, ИКБО-13-25.
Реализованы все пять этапов варианта 18. Язык — **C++17**, интерфейс — **CLI**.
Используются Qt 6 Core/Network, тесты написаны с Qt Test.

Приложение самостоятельно читает метаданные Cargo sparse index, выбирает версии,
строит граф зависимостей обходом BFS и выводит PlantUML. Дополнительно доступны
ASCII-дерево и порядок загрузки. Готовые средства получения зависимостей Cargo
в приложении не используются: HTTP, JSON, SemVer, features и обход реализованы
в исходниках проекта. Cargo нужен только для независимого сравнения результатов.

## Быстрый запуск

```sh
cd "$HOME/Documents/confPract/pract2"
./scripts/demo.sh
```

Демонстрация работает без интернета: берёт тестовый граф с общей зависимостью.
В терминале появятся описание PlantUML, ASCII-дерево и порядок загрузки.
Новые окна не открываются, так как по заданию это консольное приложение.

Для анализа реального пакета:

```sh
./run.sh --package getrandom@0.2.16 --max-depth 20 --ascii --order
./scripts/real-demo.sh
```

Для реальных пакетов нужен интернет. В `examples/real` уже сохранены текстовые
примеры для `itoa`, `getrandom`, `rand_chacha` и вывод штатного `cargo tree`.

## Сборка

Нужны компилятор C++17, CMake 3.16+, Qt 6.4+ (Core, Network, Test).
На macOS они установлены; при настройке другого компьютера с Homebrew:

```sh
brew install cmake qtbase
```

Универсальная сборка:

```sh
cmake -S . -B build
cmake --build build --config Release --parallel
ctest --test-dir build -C Release --output-on-failure
```

Если Qt не найден, передайте при конфигурации
`-DCMAKE_PREFIX_PATH="/путь/к/Qt/6.x/комплекту"`.
В macOS/Linux бинарник находится в `build/dependencies`, при Visual Studio —
в `build/Release/dependencies.exe`. Для Windows предусмотрен `run.bat`.

`run.sh` и скрипты переходят в каталог проекта. Прямой запуск бинарника
считает относительные пути от текущего рабочего каталога.
Переменная `BUILD_DIR` позволяет выбрать другой каталог сборки.

## Параметры

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `--package NAME` | обязателен | Имя crate; `name@version` закрепляет точную версию |
| `--repository SOURCE` | `https://index.crates.io/` | URL корня sparse index или путь тестового JSON |
| `--test-mode` | выключен | Использовать локальный граф с именами A..Z |
| `--ascii` | выключен | Дополнить PlantUML ASCII-деревом |
| `--max-depth N` | `5` | Максимальное расстояние от корня в рёбрах; корень имеет глубину 0 |
| `--exclude TEXT` | пусто | Исключить имена с этой подстрокой; сравнение чувствительно к регистру |
| `--order` | выключен | Дополнительно показать порядок загрузки исследованного графа |
| `--help` | — | Показать справку |

В обычном режиме имя содержит латинские буквы, цифры, `_`, `-`, начинается
с буквы и имеет длину до 64 символов. В тестовом режиме разрешены только
большие латинские буквы, без версии. Явная версия — полный SemVer.
Суффикс версии не обязателен: без него выбирается последняя стабильная версия,
не помеченная yanked. URL может иметь префикс `sparse+`.

Отрицательная/нечисловая глубина, неверный URL, отсутствующий тестовый файл,
некорректное имя, неизвестная опция или значение у флага вызывают ошибку.
Если фильтр исключает сам корневой пакет, запуск также считается ошибкой.
Пустая подстрока означает отсутствие фильтра; переводы строк в ней запрещены.

Код завершения: `0` — успех или справка, `1` — ошибка параметров, репозитория,
сети или невозможность построить порядок из-за цикла. Ошибки идут в stderr,
результат — в stdout. Финальная версия не печатает отладочный dump параметров:
он нужен только для этапа 1 и сохранён в соответствующем коммите.

## Тестовый репозиторий

JSON описывает полный список прямых зависимостей каждого узла:

```json
{
  "A": ["B", "C"],
  "B": ["D"],
  "C": ["D"],
  "D": []
}
```

Все упомянутые узлы должны быть объявлены. Повтор одинакового ребра
устраняется. Циклы и ссылки на самого себя допустимы.

```sh
./build/dependencies --package A --repository examples/diamond.json --test-mode --ascii --order
./build/dependencies --package A --repository examples/simple.json --test-mode --max-depth 1 --ascii
./build/dependencies --package A --repository examples/simple.json --test-mode --exclude B --ascii
./build/dependencies --package A --repository examples/cycle.json --test-mode --ascii
```

Образы: `simple.json` — дерево, `diamond.json` — общая зависимость,
`cycle.json` — цикл, `isolated.json` — пакет без зависимостей.

## Построение графа

Граф ориентирован от пакета к его зависимостям. Реальный узел определяется
парой `имя@версия`, тестовый — именем. BFS использует очередь, без рекурсии.
Расстояния минимальны: общая зависимость, достигнутая коротким путём, может
быть раскрыта даже при наличии более длинного пути к ней.

Узлы на границе глубины включаются, их зависимости не обходятся. Если у такого
узла остались нерассмотренные зависимости, он помечается `depth_limit` в PlantUML
и `[depth limit]` в дереве. При глубине 0 выводится только корень.
Исключённый фильтром пакет не загружается, рёбра к нему не добавляются;
обход через него прекращается. Транзитивный узел остаётся, если достижим другим
неисключённым путём.

Повторные узлы не обходятся бесконечно. Если другой родитель активировал новые
features уже известной версии, узел повторно попадает в очередь для дополнения
графа. Для защиты от чрезмерного размера установлен предел 10000 узлов.

Топологический порядок строится алгоритмом Кана: зависимости раньше родителей,
готовые независимые узлы выбираются по алфавиту. Циклический граф визуализируется,
но при `--order` выдаётся ошибка: полного корректного порядка не существует.
При глубине/фильтре порядок относится только к исследованному подграфу.

## Работа с Cargo

Источник — **корень HTTP(S) sparse index**, например `https://index.crates.io/`,
а не HTML-страница crates.io или произвольный git-репозиторий с Cargo.toml.
Путь к записи crate рассчитывается по правилам Cargo; данные читаются как
JSON Lines. Извлекаются зависимости normal/build для всех платформ,
переименованные пакеты, требования версий и features. Dev-зависимости исключены.

Поддержаны default features, именованные features, optional-зависимости,
`dep:name`, `name/feature`, `name?/feature`, объединение запросов от родителей.
Требования версий: `^`, `~`, `=`, `<`, `<=`, `>`, `>=`, wildcard `*`/`x`,
комбинации через запятую и prerelease с явным разрешением.
Yanked-версии и неизвестные новые схемы index-записей не выбираются.
HTTP-запрос имеет таймаут 15 секунд, ответ ограничен 32 МиБ; данные кешируются
только в памяти на время одного запуска. Исходные репозитории не изменяются.

Это анализатор графа, а не полный resolver Cargo. Он выбирает максимальную
подходящую версию **независимо для каждого ребра**, без глобального backtracking,
Cargo.lock, MSRV, links-конфликтов, patch/replace и resolver 2/3.
Features объединяются для одной пары имя/версия; разделения по target/host нет.
Target-условия не вычисляются: берутся зависимости всех платформ.
Git/path dependencies и переход к стороннему registry не поддержаны;
в последнем случае выдаётся явная ошибка. Приватные реестры с авторизацией
также не поддержаны. Поэтому для сложных проектов возможны отличия от Cargo.

## Визуализация

По умолчанию stdout содержит только самостоятельный блок `@startuml…@enduml`.
Корень выделен цветом. Алиасы `n0`, `n1` и т. д. формируются автоматически.
Чтобы сохранить диаграмму, запускайте собранный бинарник напрямую:

```sh
./build/dependencies --package getrandom@0.2.16 --max-depth 20 > graph.puml
```

Описание можно открыть в средстве просмотра PlantUML. Приложение формирует
текст диаграммы; рендеринг в PNG/SVG выполняет выбранное средство PlantUML.

С `--ascii` после блока PlantUML выводится дерево. `(*)` означает, что общая
зависимость уже раскрыта в другой ветке, `[cycle]` — возврат к предку текущей ветки.
Построение дерева также итеративное. С `--order` добавляется порядок загрузки;
такой комбинированный вывод уже не является одним файлом PlantUML.

## Проверки и сравнение

```sh
./scripts/check.sh
./scripts/real-demo.sh
./scripts/compare.sh
```

`check.sh` работает без внешнего интернета: запускает семь наборов тестов,
четыре тестовых графа, фильтр, глубину и проверку невозможности порядка при цикле.
HTTP-клиент тестируется на локальном сервере. Проверяются также SemVer,
активация features, общий узел, повторный обход при дополнении features и CLI.

`real-demo.sh` показывает три реальных пакета. `compare.sh` требует Cargo и
интернет: независимо запускает приложение, `cargo tree --target all`, затем
сборку getrandom через `cargo build --jobs 1 -vv` для сравнения порядка.
Cargo не вызывается из `src/`. Проекты сравнения находятся в `examples/cargo`.

Измеренные результаты и объяснения отличий: `docs/COMPARISON.md`.
План защиты: `docs/DEFENSE.md`. Результаты тестов: `docs/VALIDATION.md`.

## Функции и структура

| Файл/функции | Назначение |
| --- | --- |
| `main.cpp`: `main` | Выбор источника, построение графа, вывод и обработка ошибок |
| `config.cpp`: `readConfig`, `validateConfig`, `Config::dump` | CLI, проверка значений, dump этапа 1 |
| `version.cpp`: `parseVersion`, `compareVersions`, `matchesRequirement` | Собственная обработка SemVer |
| `repository.cpp`: `indexPath`, `parseIndex` | Путь в sparse index, разбор записей JSON Lines |
| `CargoRepository::select`, `download` | Получение HTTP-данных, кеш и выбор версии |
| `TestRepository::select` и конструктор | Чтение и проверка тестового JSON, поиск пакета |
| `features.cpp`: `activeDependencies` | Раскрытие features и выбор активных прямых зависимостей |
| `graph.cpp`: `buildGraph` | BFS, глубина, фильтр, объединение features |
| `order.cpp`: `loadOrder` | Топологический порядок и выявление невозможности сортировки |
| `render.cpp`: `plantUml`, `asciiTree` | Текст диаграммы и ASCII-дерево |
| `tests/` | Автоматические проверки всех модулей и процесса CLI |
| `scripts/` | Демонстрация, проверки и независимое сравнение с Cargo |
| `examples/` | Тестовые графы, примеры реальных результатов и проекты сравнения |

Структуры Package/Dependency описывают метаданные, FeatureRequest — активацию
features, Graph — узлы, рёбра, минимальные расстояния и границы анализа.
GraphError хранит сообщение ошибки. Конструктор CargoRepository настраивает URL.
Вспомогательные функции в анонимных пространствах имён разбирают условия версий,
поля JSON и опции features, объединяют запросы, проверяют registry и форматируют
результаты. Публичные интерфейсы описаны комментариями Doxygen в заголовках.

## История этапов

Локальный репозиторий содержит пять коммитов Conventional Commits и метки
`stage-1` … `stage-5`: конфигурация, сбор данных, BFS, порядок, визуализация.

```sh
git log --oneline --decorate
git worktree add ../pract2-stage1 stage-1
```

В этапе 1 выводятся параметры; в этапе 2 — активные прямые зависимости;
этап 3 показывает граф связей; этап 4 добавляет порядок; финальный этап выводит
PlantUML и при запросе ASCII-дерево. Публикация репозитория выполняется отдельно
со своего аккаунта. Артефакты сборки и Rust-проектов сравнения игнорируются git.

Официальные описания форматов: [Cargo index](https://doc.rust-lang.org/cargo/reference/registry-index.html),
[версии](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html),
[features](https://doc.rust-lang.org/cargo/reference/features.html),
[cargo tree](https://doc.rust-lang.org/cargo/commands/cargo-tree.html),
[PlantUML](https://plantuml.com/component-diagram).
